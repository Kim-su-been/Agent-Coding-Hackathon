## 1부. 발표 대본 (슬라이드별)

> [P1]~[P16]은 발표자료의 슬라이드 번호입니다. 구분(섹션) 슬라이드는 10~15초로 빠르게 넘깁니다.

### 오프닝 — P1 표지, P2 목차 (약 40초)

안녕하십니까, IT기획팀 김수빈입니다. 저희가 준비한 서비스는 **프로젝트 산출물 검토 보드**입니다. 메일로 오가던 산출물을 보드 하나로 모으는 서비스입니다. 한 문장으로 요약하면 세 가지입니다 — **파일은 산출물 항목에 매핑되고, 버전은 자동으로 축적되고, 현황은 한 화면에서 보입니다.**

(P2) 발표는 네 파트입니다. 첫째, PMO의 산출물 관리가 왜 어려운지 배경입니다. 둘째, Agent 개발 지침과 정본(SoT) 기반 개발 방식입니다. 셋째, 체크 보드 · 파일 매핑 · 버전 관리 · 검토 사이클 기능 소개입니다. 넷째, 기대효과입니다.

### 1. 배경 — P3~P5 (약 2분)

(P3) 첫 번째 파트, 배경입니다. PMO는 산출물을 관리해야 하는데, 산출물은 계속 수정되고, 파일은 쌓이고, 메일은 왔다 갔다 합니다.

(P4) PMO가 매번 겪는 반복 문제 네 가지입니다. 첫째, **버전 관리 어려움**. 산출물이 계속 수정되는데 최신본이 뭔지 파일명으로만 판단하고, 이전 버전은 추적이 안 됩니다. 둘째, **파일 누적**. 폴더에 파일이 계속 쌓여 어느 산출물이 어느 파일인지 파악하기 어렵습니다. 셋째, **메일 왕복**. 수집과 전달이 메일로 이루어지다 보니 수신·재전송이 반복되고, 원본 보관 위치가 분산됩니다. 넷째, **피드백 흩어짐**. "무엇을 어떻게 수정해야 하는지"라는 검토 의견이 여러 메일에 흩어져 모으기 어렵습니다. 결론은 하나입니다. **산출물 관리는 메일이 아니라, 보드 하나로 끝나야 합니다.**

(P5) 해결 방향은 관리 흐름 자체를 AS-IS에서 TO-BE로 바꾸는 것입니다. AS-IS는 메일로 제출·전달하고, 폴더에 파일이 계속 누적되고, 최신본을 파일명으로 수작업 판단하고, 피드백이 메일에 흩어집니다. TO-BE는 업로드 한 번으로 보드에 바로 제출하고, 파일이 산출물 항목에 자동 매핑되고, 버전은 자동 축적되어 최신본 포인터가 하나만 유지되고, 현황과 피드백은 한 화면에 기록됩니다. **파일은 항목에 매핑되고, 버전은 자동으로 쌓이고, 현황은 한 화면에** — 이것이 저희의 해결 방향입니다.

### 2. SoT — P6~P8 (약 2분)

(P6) 두 번째 파트, SoT입니다. Agent에게 지침을 어떻게 줬고, 기획을 어떻게 정본으로 고정했는지 말씀드리겠습니다.

(P7) Agent가 멋대로 만들지 않도록 규칙을 먼저 정본(STD-001)으로 고정했습니다. 첫째, **기술 스택 고정** — 백엔드 Java 17 · Spring Boot 3 · JPA, 프론트엔드 Vue 3(Composition API) + TypeScript, 계층형 아키텍처 · DTO 강제 · 생성자 주입입니다. 둘째, **클린 코드 규칙** — SRP, 함수 20줄 이내, 중첩은 2단계 이내로 Early Return, 서술적 네이밍, 매직 넘버 금지, 주석은 "Why"만 남깁니다. 셋째, **Guardrails** — 최소 변경 원칙, 라이브러리 추가 전 승인, 스펙이 불명확하면 임의로 가정하지 않고 질문해서 확인한 뒤 진행합니다. 그리고 Service 계층 비즈니스 로직은 **JUnit 5 Given-When-Then 단위 테스트를 필수**로 붙였습니다.

(P8) 개발은 "기획 → 정본 문서 → 코드 → 검증" 한 줄기로 진행했습니다. 정본 문서 계층은 **요구사항정의서 27건과 인수기준(AC) → 업무설계서(처리 흐름·규칙·데이터) → 화면정의서(화면 4개) → 시험시나리오** 순이고, 용어집과 코딩 규칙(STD-001)도 함께 정본화했습니다. 특히 중요한 건 사용자 결정도 문서로 남겼다는 점입니다. **D-001** — MVP 권한은 PMO 단일 역할, 로그인 없음. **D-002** — LLM 보조를 제거하고 키워드 + 벡터 하이브리드로 자체 판정. **D-003** — 배포는 로컬 실행(데모실행.bat). 모든 코드는 정본에서 시작하고, 변경 전에 SoT를 조회하고, 구현 후에는 문서와 일치하는지 검증합니다.

### 3. 기능 소개 — P9~P13 (약 4분)

(P9) 세 번째 파트, 기능 소개입니다. 체크 보드, 파일→항목 매핑, 버전 관리, 검토 사이클 네 가지입니다.

(P10) 첫 번째 기능, **체크 보드(대시보드)**입니다. "이번 차수 산출물 다 들어왔나?"를 한 화면에서 즉시 답합니다. 차수별 진행률과 상태 요약 배지가 한 줄로 보입니다. 예를 들어 "필수 5종 중 4종 접수, 1종 미제출, 1종 보완 필요"입니다. 대장 표에는 산출물 항목 · 상태 · 최신본 링크 · 버전 · 접수일 · **매칭 근거**까지 보이고, 행마다 최신본 1개만 표시해 전체 버전은 상세 화면에서 봅니다. 엑셀 대장(xlsx) 다운로드와 폴더 압축 내보내기(최신본만, old는 별도 폴더)도 지원합니다. 현황 질문에 근거 기반으로 바로 답하는 대시보드입니다.

(P11) 두 번째 기능, **파일 → 항목 매핑**입니다. PMO가 파일을 찾아 넣는 게 아니라, **파일이 자기 항목을 찾아옵니다**. 다섯 단계로 동작합니다. 다중 업로드 → `storage/차수/`에 원본 저장 → SHA-256 해시로 중복 판정 → 키워드 + 2-gram TF-IDF 벡터 유사도의 하이브리드 매칭으로 항목 제안 → 근거를 보고 PMO가 수락하면 대장에 연결. 후보가 1개면 행 연결 제안(수락 시 즉시 접수), 2개 이상이면 근거와 함께 나란히 제안하고 모호하면 선택을 보류, 0개면 신규(자동등록) 제안에 PMO 승인을 반영합니다. 핵심은 **판정이 연결 · 신규 · 중복 세 갈래뿐**이라는 것, 그리고 **PMO가 수락하기 전까지는 어떤 행도 바뀌지 않는다**는 점입니다.

(P12) 세 번째 기능, **버전 관리**입니다. 원칙은 "최신본은 하나, 이전 버전은 전부 보존"입니다. 수락 시점에 파일명이 자동 생성되고, 최신본이 갱신되면 이전 버전은 old로 수집되어 언제든 열람·다운로드할 수 있습니다. 같은 파일명을 다시 올리면 새 버전 제안(v0.1 → v0.11)이 만들어지고, 내용이 같으면 해시로 중복 무효 처리됩니다. 확정된 행에 재제출이 들어오면 확인 팝업을 띄우고, 확인하면 상태 전환과 함께 새 버전이 등록되고, 취소하면 최신본은 그대로입니다. **"몇 번째 버전이 최신인지" 고민은 시스템이 대신 판단합니다.**

(P13) 네 번째 기능, **검토 사이클과 감사 로그**입니다. 행 상태는 미제출 → 접수 → 보완 필요(사유) → 확정으로만 흐르고, 검토하기에서 검토완료 또는 보완 필요(사유)를 지정합니다. 보완 필요가 되면 재접수 사이클이 반복되고, **허용되지 않는 전환은 서비스에서 거부**합니다. 검토 파일 모음 화면에서 검토 필요 항목의 최신 제출 파일을 단계·항목·상태·버전으로 모아 보고, **감사 로그(AuditLog)**에 수락·확정·보완·매칭 근거까지 모든 변경 이력을 기록합니다. 상세 화면에서는 파일 버전 내역을 최신순·old 구분으로 확인할 수 있습니다. 피드백이 메일에 흩어지지 않고 대장과 감사 로그에 남습니다.

### 4. 기대효과 및 마무리 — P14~P16 (약 1분 30초)

(P14) 마지막 파트, 기대효과입니다. PMO의 반복 업무를 줄이고, 산출물 데이터의 신뢰를 만듭니다.

(P15) 기대효과 여섯 가지입니다. **PMO** — 진행률·미제출·보완 현황을 한 화면에서 즉시 확인해 "이번 차수 산출물 다 들어왔나?"를 근거 기반으로 답합니다. **버전 관리** — 자동 부여·최신본 포인터·old 보존으로 이전 버전 추적이 되고 최신본 판단 실수가 사라집니다. **수집·전달** — 메일 왕복이 제거되고 중복 파일은 자동 무효화됩니다. **피드백** — 검토 → 보완 필요 → 재접수 사이클이 대장에 기록되고 감사 로그로 추적됩니다. **품질·신뢰** — 확정본 보호·상태 전환 규칙 강제·해시 기반 중복 판정으로 데이터 정합성을 확보합니다. **확장성** — 기준대장 템플릿을 설정 파일로 제공해(하드코딩 없음) SI 표준 산출물 목록을 프로젝트별로 재사용합니다. 검증도 했습니다 — TC-01~21 화면 관찰에 더해, **임의 파일 100개 중 기대 매핑과 서비스 판정 일치 97%**를 실측했습니다. 매핑 판정은 파일당 평균 약 8ms(100건 실측), 불일치 3건은 접수 화면에서 항목을 골라 바로 수정할 수 있고, **확정은 항상 PMO의 몫**입니다.

(P16) 감사합니다. 프로젝트 산출물 검토 보드 — 우리금융그룹 × 수호천사동양생명 Agent Coding Hackathon 산출물이었습니다. 질문 환영합니다.

### ⚠ 발표 전 자료 정합성 체크(질문 대비)

IT개발팀 청중은 자료의 숫자 불일치를 잘 잡습니다. 아래 3건은 발표 전에 확인·수정하면 좋습니다.

1. **P8 "시험시나리오 TC-01 ~ 13" ↔ P15 "TC-01~21"**: 현재 SoT 시험시나리오(TS-outputhub-P01)는 **TC-01~21**입니다. P8 수치를 21로 갱신하거나, 질문이 나오면 "현재 SoT 기준 TC-01~21"로 답합니다.
2. **P10 진행률 기준**: 요구사항정의서(REQ-outputhub-002·016)는 완료율을 **검토완료 기준**으로 정의하는데, 시험시나리오 TC-09 실측의 "진행률 80%"는 접수 기준(4종/5종)입니다. 발표 전 구현 화면의 진행률 계산 기준을 확인해 두고, 질문 시 "완료율 지표는 검토완료 기준 원칙, 접수 현황은 배지로 별도 표시"처럼 화면별 기준을 구분해 답합니다.
3. **P12 예시 파일명 "견적서_v2_20261119.pdf"**: 수락 시점 파일명 규칙(REQ-outputhub-022)은 `{항목}_v0.1_{날짜}`부터 시작해 검토완료 시 `v1.0`입니다. 슬라이드 예시는 원본 파일명(견적서_v2.pdf)에 날짜를 붙인 그림이라 규칙 파일명과 맞지 않습니다. 예시를 규칙 파일명으로 고치거나, 질문 시 "그림은 원본 파일명 예시, 실제 저장 파일명은 REQ-outputhub-022 규칙"으로 구분해 답합니다.

## 2부. 예상질문·답변 (IT개발팀 청중 기준)

> 답변마다 괄호 안에 근거(ID)를 적어 두었습니다. 개발팀 청중에게는 근거 ID를 대는 것이 가장 강한 답변입니다. 상황에 맞게 줄이거나 붙여 쓰세요.

### A. 아키텍처 · 기술 스택

**Q1. 계층 구조는 어떻게 되어 있습니까? 계층 간 의존 방향과 역할 분리는요?**

A. Controller → Service → Repository 단방향 계층 구조입니다. Controller는 HTTP 요청/응답과 `@Valid` 입력 검증만 하고 비즈니스 로직을 갖지 않고, Service가 핵심 비즈니스 로직과 트랜잭션 경계를 담당하며, Repository는 데이터 접근만 합니다. Entity를 API에 직접 노출하지 않고 전용 DTO를 강제했고, 생성자 주입을 쓰며, 커스텀 예외를 `@RestControllerAdvice`로 전역 처리합니다. 매칭 판정(REQ-outputhub-004)·버전 판정 로직은 Service 계층 도메인 로직으로 분리했습니다. 도메인은 round(차수)·deliverable(산출물 항목)·submission(접수)·version·audit으로 나눕니다. (STD-001 §3, §9)

**Q2. 왜 H2 파일 모드입니까? 실제 운영으로 가면 DB는 어떻게 합니까?**

A. MVP의 전제가 로컬 실행(D-003)이기 때문입니다. 메타데이터만 H2 파일 모드에 두고, 업로드 원본은 로컬 `storage/<차수>/` 폴더에 보관합니다(NFR-outputhub-002, REQ-outputhub-003). 데이터 접근은 전부 JPA로 하므로 운영화 시 다른 RDBMS로의 전환 부담은 낮습니다. 단, 다중 접속·백업·가용성은 MVP 범위 밖이라, 운영화 단계에서 DB 이관과 저장소·백업 정책을 별도 설계해야 하는 점을 명확히 말씀드립니다.

**Q3. 로그인도 없이 보안은 괜찮습니까?**

A. MVP는 PMO 단일 역할·로그인 없음을 사용자 결정(D-001)으로 명시하고, 제출자 전용 화면·권한 검증 체계는 범위 밖으로 **일부러 뺐습니다**. 사내 로컬 사용 전제의 MVP이고, 권한 체계는 첫 확장 과제입니다. 확장 시 Spring Security 또는 사내 SSO를 도입하는 지점은 Controller 앞단의 인증·권한 계층으로 분리해 두면 기존 Service 로직에 미치는 영향이 작습니다.

**Q4. 프론트엔드 구조는 어떻게 되어 있습니까?**

A. Vue 3 `<script setup>`(Composition API) + TypeScript입니다. 컴포넌트는 200줄 이내로 UI·기능 단위로 분리하고, API 호출·복잡한 가공·상태 로직은 composables/ 디렉터리로 분리하며, axios·fetch 직접 호출 대신 api/ 계층 모듈로 통신합니다. props는 직접 수정하지 않고 emit·Pinia로 상태 변경을 처리하고, API 호출 시 로딩(isLoading)·에러(error) 상태를 반드시 처리합니다. (STD-001 §4, §7)

**Q5. 이 스택을 고른 이유가 무엇입니까? 사내 표준과는 어떻게 맞춥니까?**

A. 기술 스택 자체가 프로젝트 제약(NFR-outputhub-001, 첨부 Agent Instructions)으로 고정돼 있었습니다 — Java 17+ · Spring Boot 3.x · Spring Data JPA, Vue 3 + TypeScript. Java/Spring 계열은 사내 SI 표준 개발 스택과 호환성이 높고, 화면 4개 규모의 MVP에 Vue 3 + TS가 적합하다고 판단했습니다. 실제 사내 도입을 검토할 때는 사내 아키텍처 표준·보안 심사 기준으로 재확인하는 단계가 필요합니다.

### B. 매칭 알고리즘

**Q6. "하이브리드 매칭"을 구체적으로 어떻게 계산합니까?**

A. 두 점수를 합산합니다. ① 규칙 점수 — 파일명과 문서 제목·시트 헤더에서 추출한 키워드로 산출물 항목을 매칭하는 점수, ② 벡터 유사도 — 파일명을 2-gram으로 잘라 TF-IDF 코사인 유사도를 계산. 이 합산 점수로 후보를 정하고, 판정은 3갈래입니다 — 기존 행 연결 / 미매칭 → 신규 자동 등록 / 동일 해시 → 중복. 매칭 키워드 규칙과 벡터 가중치·기준값은 코드에 하드코딩하지 않고 설정 파일로 관리합니다. (REQ-outputhub-004·014)

**Q7. LLM을 뺀 이유가 무엇입니까? 요즘 흐름과 반대 아닙니까?**

A. 사용자 결정(D-002, 2026-11-19)입니다. 판정의 책임이 PMO 수락에 있고, 근거 설명 가능성·결정성(같은 입력에 같은 판정)·오프라인 동작·비용 측면에서 규칙+벡터가 MVP에 적합했습니다. 미매칭 파일도 LLM 없이 닫힙니다 — 항목 드롭다운 직접 선택(REQ-outputhub-021) 또는 신규 자동등록 승인(REQ-outputhub-005). LLM 보조는 근거 설명 자동화 같은 확장 단계의 후보로 남겨 둡니다.

**Q8. 잘못된 항목에 연결되는 오매칭은 어떻게 막습니까?**

A. 설계 원칙이 "**자동은 제안까지만, 수락은 사람**"입니다. 판정 결과를 행에 바로 반영하지 않고 근거를 보여 주고(REQ-outputhub-013), 모호하면 후보 2개를 근거와 함께 나란히 제안해 선택을 보류합니다(AC-004-2). 제안 카드마다 항목 드롭다운이 있어 제안이 틀렸으면 PMO가 다른 항목을 골라 수락할 수 있고(REQ-outputhub-025), 수락 전까지는 어떤 행도 바뀌지 않습니다. 실측으로 임의 파일 100개 중 기대 매핑과 판정 일치 97%, 불일치 3건은 접수 화면에서 즉시 수정했습니다.

**Q9. 매칭 임계값과 가중치는 어떻게 정했습니까? 후보 점수가 동률이면?**

A. 가중치·기준값은 설정 파일로 관리해 코드 수정 없이 조정합니다(REQ-outputhub-014). 후보 2개 동률 처리(예: TC-03의 `투입계획_및_WBS.xlsx` — 두 키워드 공존)의 판정 임계는 SoT에 "[확인 필요]"로 남아 있는 항목이고, 이런 부분을 개발팀과 함께 확정하면 좋겠습니다. 동률·모호 케이스는 어느 쪽으로도 강제하지 않고 선택 보류가 기본 동작입니다. (TC-03, TS-outputhub-P01 "남은 것")

**Q10. 한국어 파일명에서 2-gram TF-IDF가 잘 동작합니까?**

A. 2-gram은 문자 단위 특징이라 별도 형태소 분석 없이 한국어 파일명에 적용됩니다. 규칙 키워드가 분절·부재한 케이스도 벡터만으로 연결 제안된 실측이 있습니다 — `사업 수행 계획서_초안.pdf`, `W.B.S_기준일정.xlsx`, `운영자메뉴얼_장애대응.pdf` 모두 규칙 키워드 불일치 상태에서 벡터 유사도로 연결 제안되어 통과했습니다. (TS-outputhub-P01 §4 매칭 검증)

**Q11. 매칭 성능은 어느 정도입니까? 대용량이면 어떻게 됩니까?**

A. 매핑 판정이 파일당 평균 약 8ms(100건 실측)입니다. 계산이 파일명 대상 2-gram TF-IDF 코사인이라 외부 벡터 DB·색인 서버 없이 서비스(MatchService)에서 즉시 계산되고, 항목 규모가 기본 23종(REQ-outputhub-017) 수준이라 충분합니다. 대용량·다차수 확장 시 응답 시간 목표는 비기능 요구(NFR-outputhub-005)에 [확인 필요]로 남아 있어, 운영화 전에 목표치를 합의해 부하 테스트로 검증하는 단계가 필요합니다.

### C. 버전 · 파일 관리

**Q12. 버전 체계가 v0.1 → v0.11인데 SemVer 같은 일반 관례와 다릅니다. 의도가 무엇입니까?**

A. 의도는 **버전대역으로 단계를 구분**하는 것입니다. 수락 시점마다 0.01씩 올라가고(0.1 → 0.11 → 0.12 …), 검토완료(확정) 처리 시 최신본 파일명이 `{항목}_v1.0`이 됩니다. 즉 0.x는 검토 전, 1.0은 검토완료본입니다. 검토완료 뒤 재수락 버전은 v1.01부터 이어집니다. 소프트웨어 의존성 SemVer와 목적이 다른 **문서 버전 체계**이고, 확정 여부가 파일명만 봐도 드러나는 것이 핵심입니다. (REQ-outputhub-022, AC-022-1·022-2)

**Q13. 이건 Git 쓰면 되는 것 아닙니까?**

A. 목적이 다릅니다. Git은 개발자의 이력 관리 도구지만, 이 서비스의 사용자 모델은 PMO·수행사 같은 비개발 참여자의 업로드 → 매핑 제안 → 수락 → 검토완료 워크플로와 대장 집계입니다. 커밋·브랜치 개념을 노출하는 대신, 파일 자동 명명 + 최신본 포인터 + old 보존으로 동일한 추적성을 업무 언어로 제공합니다. 내부적으로는 단순 스냅샷 보관이며, 덮어쓰기는 없습니다(이전 버전은 항상 old로 열람 가능).

**Q14. 확정본 보호는 정확히 어떻게 구현됩니까?**

A. 검토완료(확정) 행에 새 파일의 수락이 시도되면 확인 팝업("검토완료된 항목입니다. 정말 다시 업로드하시겠습니까?")이 뜹니다. 확인하면 상태가 검토 필요(검토전)로 전환되고 새 파일이 새 버전으로 등록되며 이전 확정본은 old로 보존됩니다. 취소하면 행 상태·최신본은 불변이고 제안은 후보로만 대기합니다(AC-008-1·008-2). 그리고 이 전환은 팝업 승인 시에만 허용되고, 그 외 허용되지 않는 전환은 서비스에서 거부합니다. (REQ-outputhub-008·010)

**Q15. 중복 판정은 언제 합니까? 업로드 뒤에 내용을 바꾸면 우회되지 않습니까?**

A. 두 시점에서 검증합니다. ① 업로드 시점 — SHA-256 해시로 등록된 버전과 내용을 비교하고, ② 수락·승인 시점 — 등록 직전에 다시 해시를 확인합니다. 그래서 업로드와 수락 사이에 내용을 바꾸거나, 같은 파일을 경쟁적으로 수락해도 등록이 막힙니다(REQ-outputhub-006). 파일명과 무관하게 내용 기준이며, 같은 내용이면 중복 표시 + 대장 행 수에 이중 계산하지 않습니다. 중복 안내는 응답 전용 1회성 알림이라 접수함을 다시 열면 사라집니다.

**Q16. 원본 파일 저장 구조와 백업은 어떻게 합니까?**

A. 원본은 `storage/<차수>/`에, 메타데이터는 H2 파일 모드 DB에 둡니다(NFR-outputhub-002). MVP 기준 백업은 "storage 폴더 + DB 파일 복사" 수준이고, 운영화 시에는 저장소(공유 스토리지·오브젝트 스토리지) 정책과 백업 주기·보존 기간 설계가 필요한 영역입니다. 이번에 폴더 내보내기(최신본만, old는 별도 폴더, REQ-outputhub-011)를 두어 산출물 인수인계 단위의 백업 경로는 이미 확보돼 있습니다.

**Q17. 파일 용량·확장자 제한은 어떻게 됩니까?**

A. 현재 정본에는 용량·확장자 제한 요구가 명시돼 있지 않습니다(MVP는 업로드 기반 접수). 필요하다면 후속 요구로 정의해야 하고, 요구사항정의서에 추가하는 프로세스(SoT 변경)로 반영하겠습니다. 지금 답변드리는 게 정직한 범위입니다.

### D. 상태 전환 · 감사

**Q18. 상태 전환 규칙(상태 머신)은 어떻게 강제합니까?**

A. 행 상태는 **미제출 → 접수 → (보완 필요 ⇄ 보완본 재접수) → 확정**으로만 변합니다. 확정은 PMO만 수행하고, 검토완료 → 접수(검토전) 전환은 재업로드 확인 팝업 승인 시에만 허용됩니다(REQ-outputhub-010). 허용되지 않는 전환 요청은 서비스에서 거부하며, 실측으로 확정 상태 재수락을 409로 거부하는 사례(TC-06)가 시험시나리오에 있습니다. 전환 로직은 Service 계층에 있어 화면 우회로도 규칙을 우회할 수 없습니다.

**Q19. 감사 로그(AuditLog)에는 무엇까지 기록됩니까?**

A. 접수·승인·확정·상태 변경마다 기록하고, 매칭 근거까지 남깁니다(REQ-outputhub-015, NFR-outputhub-004). 예를 들어 제안 카드에서 제안과 다른 항목을 골라 수락하면 근거에 "검토대기에서 산출물 항목을 직접 선택"이 기록되고(TC-17), 서버 시작 정합화가 발생하면 "파일명 정합화" 로그가 남습니다(TC-21). 검토완료가 되면 파일 버전 내역이 감사 이력 표에 시간순으로 병합되어 한 항목의 전체 이력이 한 화면에 보입니다(REQ-outputhub-024).

**Q20. "서버 시작 때 파일명 정합화"가 왜 필요합니까?**

A. 검토완료 기록이 규칙 파일명(`{항목}_v1.0.{확장자}`)·재수락 버전 기준에서 벗어나 있으면(예: 낡은 빌드로 확정되어 원본 파일명이 남은 기록) 서버 시작 때 규칙대로 바로잡습니다(TC-21). 규칙대로인 기록은 그대로 두고 재수락 카운터만 v1.0으로 맞추며, 파일 누락 기록은 건너뛰고 점검을 계속합니다 — 데이터 정합성을 회복하되 가용성을 깨지 않는 방향입니다. (REQ-outputhub-022, AC-022-3)

### E. 확장성 · 운영 · 검증

**Q21. 다른 프로젝트·차수에서 재사용할 수 있습니까?**

A. 재사용이 설계 목표 중 하나입니다. 기본 산출물 목록은 착수(4)·분석(2)·설계(5)·개발(2)·테스트(4)·인수인계 및 종료(5)·PMO(1) **23종**을 설정 파일 템플릿으로 제공하고 코드 하드코딩은 금지합니다(REQ-outputhub-014·017). 매칭 키워드 규칙과 벡터 가중치·기준값도 같은 설정 파일 체계입니다. PMO는 프로젝트별로 항목을 직접 추가·삭제할 수 있고(REQ-outputhub-019), 차수(Round) 단위로 기준대장을 새로 등록합니다.

**Q22. 공유 폴더를 자동으로 스캔해서 수집하게 하면 안 됩니까?**

A. MVP는 업로드 기반 접수로 명확히 범위 밖으로 뺐습니다(REQ-outputhub-P01 개요 "제외"). 이유는 접수의 책임 소재입니다. 이 서비스의 핵심은 "무엇이 접수됐는가"가 PMO의 수락이라는 명확한 사건을 갖는 것이고, 폴더 스캔은 그 사건 없이 파일만 늘어나게 합니다. 자동 스캔은 향후 확장 후보이지만 접수 정책(누가 접수로 인정할 것인가)을 먼저 정해야 합니다.

**Q23. 그룹웨어·다른 시스템과 연동 계획이 있습니까?**

A. MVP는 로그인 없는 단독 로컬 실행(D-001·D-003)이라 외부 연동이 없습니다. 확장 방향으로는 ① 인증(SSO) ② 제출자 역할 도입(제출자 전용 화면) ③ 접수 현황 알림 연계 순이 자연스럽고, 연계는 API 지점으로 설계해 두었습니다. 구체 범위는 운영 조직의 시스템 현황 확인 후 정하겠습니다.

**Q24. 테스트는 어떻게 검증했습니까?**

A. 두 층입니다. ① 단위 테스트 — Service 계층 비즈니스 로직에 JUnit 5 Given-When-Then, 정상+예외 케이스를 필수로 작성합니다(NFR-outputhub-003, STD-001 §6). 예: 동일 해시 중복 판정(TC-05), 버전 갱신 시 old 수집(TC-08), 모호 파일 후보 2개 제안(MatchServiceTest). ② 시나리오 검증 — 시험시나리오 TC-01~21을 화면 관찰 + JUnit + API 실행으로 검증했습니다(로컬 gradle bootRun, 포트 8080). 매핑은 별도로 임의 파일 100개 실측(97% 일치)을 수행했습니다.

**Q25. 배포와 실행 방법은요?**

A. 로컬 실행입니다(D-003). 데모실행.bat으로 올리거나, 백엔드는 Spring Boot 실행(gradle bootRun, 포트 8080), 프론트엔드는 Vue 정적 빌드를 서빙하고, DB는 H2 파일 모드입니다. 배포 자동화는 MVP 범위 밖으로 명시적으로 제외했습니다.

**Q26. MVP 이후 로드맵은 어떻게 보고 계십니까?**

A. MVP에서 명시적으로 제외한 것부터가 로드맵입니다. ① 제출자 역할·권한 체계(로그인, D-001) ② 공유 폴더 자동 스캔 ③ DB 이관·저장소 정책 ④ 배포 자동화 ⑤ 매칭 보조(LLM 근거 설명 자동화, D-002에서 남겨 둔 후보) ⑥ 운영 성능 목표 확정(NFR-outputhub-005). 우선순위는 "PMO 반복 업무 절감 효과를 먼저 검증, 그다음 사용자 확장" 순서로 본다고 말씀드리겠습니다.

**Q27. 로그인이 없는데 "제출자"는 어떻게 파일을 내나요?**

A. MVP에서는 제출자 전용 화면이 범위 밖(D-001)이라, 수행사에서 메일 등으로 전달한 파일을 PMO가 접수함에 업로드하는 흐름입니다. 서비스가 해결하는 것은 PMO의 수집·대장·버전·검토 관리이고, 제출자가 직접 올리는 경험은 다음 단계(제출자 역할·권한)의 과제입니다.

### F. 발표자료 자체에 대한 지적 대비

**Q28. 8쪽은 시험시나리오가 TC-01~13인데 15쪽은 TC-01~21입니다. 어느 게 맞습니까?**

A. 지적 감사합니다. 현재 정본 시험시나리오(TS-outputhub-P01) 기준은 **TC-01~21**이고 15쪽이 정확합니다. 8쪽 수치는 갱신 전 값으로 발표 자료를 수정하겠습니다. (해결 후에도 정본 우선 원칙으로 답)

**Q29. 진행률 %가 접수 기준입니까 검토완료 기준입니까?**

A. 요구사항정의서는 완료율을 **검토완료 기준**으로 정의합니다(REQ-outputhub-002·016), 접수 현황은 "필수 5종 중 4종 접수" 같은 배지로 별도 표시합니다. 시연 시나리오(TC-09)의 "진행률 80%"는 접수 기준 실측이라 기준이 섞여 보일 수 있는데, 이는 구현 화면 기준으로 확인해 자료와 함께 정리하겠습니다.

**Q30. 12쪽 예시 `견적서_v2_20261119.pdf`는 버전 규칙(REQ-outputhub-022)과 맞지 않는 것 같습니다.**

A. 맞습니다. 실제 수락 시점 파일명은 `{항목}_v0.1_{날짜}`부터 시작해 검토완료 시 `{항목}_v1.0`입니다(REQ-outputhub-022, TC-13·TC-14). 슬라이드 예시는 원본 파일명(견적서_v2.pdf)에 날짜를 붙인 그림이므로, 발표 전 규칙 파일명 예시로 정합화하겠습니다.

## 3부. 답변 요령 (IT개발팀 청중 전용)

1. **근거 ID로 답한다.** 이 청중은 문서 기반 검증을 아는 사람들입니다. "REQ-outputhub-004", "TC-21", "STD-001"처럼 근거 ID를 대면 발표 내용이 개인 의견이 아니라 정본 문서의 요구라는 것이 즉시 전달됩니다.
2. **MVP 경계는 숨기지 않는다.** 로그인 없음(D-001), 로컬 실행(D-003), 공유 폴더 스캔 제외 같은 것은 약점이 아니라 "범위를 명시적으로 결정하고 기록했다"는 설계 성숙도의 증거다. "범위 밖으로 명시적으로 뺐고, 결정 기록 D-00X에 남아 있습니다"가 기본 답 형식.
3. **모르면 질문으로 받는다.** "스펙이 불명확하면 임의 가정 금지, 질문하여 확인 후 진행"이 이 프로젝트의 Agent 지침(Guardrails)이다. Q&A에서도 같은 원칙 — 모르는 것은 "확인 후 답하겠습니다"로 받고 기록하는 것이 프로젝트 방식 그 자체다.
4. **수치는 실측된 것만 쓴다.** REQ 27건, 화면 4개, TC-01~21, 필수 5종, 기본 목록 23종, 매핑 일치 97%·파일당 약 8ms(100건 실측), v0.1→v0.11→v1.0. 이 범위를 벗어나는 숫자는 만들지 않는다.
5. **Q&A 시간이 부족하면 우선 답변 순서**: Q6(하이브리드 매칭 산식) → Q7(LLM 제거 이유) → Q3(로그인·보안) → Q12(버전 체계) → Q2(H2·운영 전환).

# 발표 자료 기초 정리 — OutputHub (산출물 접수·검토 보드)

> 근거: Agent_Instructions.md, deepwiki/sot/업무/outputhub/* (REQ·BD·SCR·TS·GLO), Agent-Coding-Hackathon/README.md, 백엔드/프론트 구조

## 1. 배경 (문제 정의)

PMO가 산출물 관리에서 겪는 4가지 반복 문제:

| # | 문제 | 현재 방식의 한계 |
|---|------|------------------|
| 1 | **버전 관리 어려움** | 산출물이 계속 수정됨 → "몇 번째 버전이 최신인지" 파일명으로만 판단, 이전 버전 추적 불가 |
| 2 | **파일 누적** | 파일이 폴더에 계속 쌓여 어느 산출물이 어느 파일인지 파악 곤란 |
| 3 | **메일 왕복** | 수집·전달이 메일로 이루어져 수신·재전송 반복, 원본 보관 위치가 분산 |
| 4 | **피드백 수집** | "무엇을 어떻게 수정해야 하는지" 검토 의견이 흩어져 모으기 어려움 |

→ 해결 방향: **메일 대신 보드로 제출**하고, **파일을 산출물 항목(대장 행)에 매핑**해 **버전이 자동으로 쌓이고**, 검토 피드백과 진행 현황이 **한 화면**에서 보이는 구조.

## 2. SoT — Agent 지침과 작업 방식

### 2-1. Agent에게 준 지침 (Agent_Instructions.md)

- **역할 정의**: 클린 코드·유지보수성 최우선 시니어 풀스택 개발자
- **기술 스택 고정**: Backend Java 17 + Spring Boot 3 + JPA / Frontend Vue 3 (Composition API, `<script setup>`) + TS
- **클린 코드 규칙**: SRP, 함수 20줄 이내, 중첩 2단계 이내(Early Return), 서술적 네이밍, 매직 넘버 금지, 주석은 "Why"만
- **아키텍처 규칙**: 계층형(Controller/Service/Repository), DTO 강제, 생성자 주입, 전역 예외 처리 / Vue는 views·components·composables·api·types 분리, API 통신은 api/ 계층으로
- **행동 제약(Guardrails)**: 최소 변경 원칙, 라이브러리 추가 전 승인, 스펙 불명확 시 임의 가정 금지(질문 후 진행)
- **테스트**: Service 계층 JUnit 5 Given-When-Then 단위 테스트 필수

### 2-2. SoT(Single Source of Truth) 진행 방식

1. **온보딩**: `sot-init`으로 작업 폴더 SoT 초기 구조 생성(2026-11-19, 사용자 확인) — `deepwiki/sot/` 하위에 표준·업무 문서 배치
2. **정본 문서 계층** (outputhub 업무):
   - `REQ-outputhub-P01` — 요구사항정의서: 27개 요구사항 + 인수 기준(AC)까지 정의
   - `BD-outputhub-P01` — 업무설계서: 업로드 접수 처리 흐름(시퀀스 다이어그램), 업무 규칙, 데이터 모델
   - `SCR-outputhub-P01` — 화면정의서: 화면 4개의 항목·동작·API·검증 정의
   - `TS-outputhub-P01` — 시험시나리오: TC-01~13으로 합격 기준을 화면 값으로 관찰 가능하게 정의
   - `GLO-OUTPUTHUB-001` — 용어집, `STD-001` — Agent 코딩 규칙
3. **사용자 결정 기록**: 불명확한 기획은 임의로 진행하지 않고 ask_user로 결정 — 예) MVP 권한은 PMO 단일 역할·로그인 없음(D-001), 매칭은 LLM 보조 제거 → 키워드+벡터 하이브리드 자체 판정(D-002), 배포는 로컬 실행(D-003)
4. **코드 변경 전 SoT 조회 → 구현 → 검증**: 검증 래퍼·문서 참조 검사기(`tools/`)로 구현물이 정본 문서와 일치하는지 점검

## 3. 기능 소개 (구현된 것)

**화면 4개** (SCR-outputhub-01~04) + 백엔드 API:

| 화면 | 기능 |
|------|------|
| **체크 보드** (대시보드) | 차수별 진행률 %, 요약 배지("필수 5종 중 4종 접수 · 1종 미제출 · 1종 보완 필요"), 대장 표(항목·상태·최신본 링크·버전·매칭 근거), 엑셀/폴더 내보내기 |
| **제출 파일함** | 파일 다중 업로드 → 원본 `storage/<차수>/` 저장 → SHA-256 해시·중복 판정 → **하이브리드 매칭(키워드 + 파일명 2-gram TF-IDF 벡터 유사도)** 으로 항목 매핑 제안(근거 표시) → PMO 수락 |
| **산출물 상세·내보내기** | 파일 버전 내역(모든 버전 최신순·old 구분, 각 행 다운로드), 감사 이력, 검토하기 → 검토완료/보완 필요 지정(사유), 확정 |
| **검토 파일 모음** | 검토 필요 항목의 최신 제출 파일을 단계·항목·상태·버전·링크로 모아보기 |

**핵심 도메인 기능:**

- **파일 → 항목 매핑**: 매칭 후보 1개면 행 연결 제안, 2개 이상이면 근거와 함께 나란히 제안(모호 시 선택 보류), 후보 0개면 **신규(자동등록)** 제안(필수=아니오, PMO 승인 반영). 드롭다운으로 항목 직접 선택도 가능
- **버전 관리**: 수락 시 `{항목}_v{버전}_{날짜}` 파일명 자동 부여, 최신본 갱신 + 이전 버전 old 수집. 동일 파일명 재업로드는 새 버전 제안(v0.1 → v0.11), 동일 해시(내용 같음)는 중복 무효 처리
- **확정본 보호**: 확정된 행에 재제출 시 확인 팝업 → 확인 시 상태 전환 + 새 버전, 취소 시 최신본 불변
- **상태 전환 관리**: 미제출→접수→확정 / 보완 필요(사유 표시)→재접수, 허용되지 않는 전환은 서비스에서 거부
- **감사 로그(AuditLog)**: 수락·확정·보완·매칭 근거까지 모든 변경 이력 기록
- **내보내기**: 엑셀 대장(xlsx), 폴더 압축(최신본만, old 별도)
- **데모 실행**: `데모실행.bat` 하나로 서버(8080) 기동 + 브라우저 오픈, H2 파일 모드

**구현 구조** (지침 준수): backend 도메인형 패키지(`api/` Controller 5개, `domain/` Entity 8개, `service/`·`match/`·`storage/`), frontend views 4 + components 4 + api 계층

## 4. 기대효과

| 관점 | 효과 |
|------|------|
| PMO | 진행률·미제출·보완 현황을 **한 화면에서 즉시 확인** — "이번 차수 산출물 다 들어왔나?"를 근거 기반으로 답함 |
| 버전 관리 | 버전 자동 부여·최신본 포인터·old 보존으로 **이전 버전 추적 및 다운로드 가능**, 최신본 판단 실수 제거 |
| 수집·전달 | 메일 왕복 제거 — 업로드 한 번으로 접수·매핑·접수 완료, 중복 파일은 자동 무효화 |
| 피드백 | 검토 파일 모음 + 상세 화면에서 **검토→보완 필요(사유)→재접수** 사이클이 대장에 기록, 감사 로그로 이력 추적 |
| 품질·신뢰 | 확정본 보호, 상태 전환 규칙 강제, 해시 기반 중복 판정으로 데이터 정합성 확보 |
| 확장성 | 기준대장 템플릿을 설정 파일로 제공(하드코딩 없음) → SI 표준 산출물 목록을 프로젝트별 재사용 가능 |
| 검증 가능성 | 시험시나리오(TC-01~21)로 합격 기준을 화면 값으로 관찰 + 임의 파일 100개를 만들어 기대 매핑과 서비스 판정이 일치하는지 판정 — 일치 97% 실측(JUnit으로 재현), 불일치 3건은 접수 화면에서 항목을 골라 바로 수정 가능(제안은 시스템, 확정은 PMO) |
